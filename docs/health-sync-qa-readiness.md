# 갤럭시워치 연동 사전 검수

기준은 최종 통합 브랜치의 `0d902a3`이다. 배포된 공식 APK v0.1.1에는 기존 v0.1.0의 DEX와 브리지 자산이 그대로 들어 있다. APK의 Health Connect 관련 메시지와 `/api/mobile/health-sync` 경로를 확인했다. 새 테스트는 합성 기록과 격리 DB를 사용한다.

## 기록이 화면에 나타나는 조건

1. 갤럭시워치 기록은 삼성 헬스를 거쳐 Health Connect에 공유된다. 삼성 헬스 쪽의 기록 공유 여부, 달잠의 Health Connect `READ_SLEEP`, 달잠 내부의 선택 출처와 서버 전송 동의가 각각 필요하다.
2. 배포 APK는 최근 30일의 `SleepSessionRecord`를 선택한 출처로 페이지 단위 조회한다. 최초 출처 선택 시 이 기간에 접근 가능한 수면 기록이 있는 출처를 나열하며, 삼성 헬스 패키지는 `com.sec.android.app.shealth`이다. 기록의 종료 시각은 조회 창 안에 있어야 한다.
3. 세션의 `stages`에서 깨어 있음·침대 밖·수면 중 각성은 `wake`, 단계가 특정되지 않은 수면은 `unspecified`, 얕은 수면은 `core`, 깊은 수면은 `deep`, REM은 `rem`으로 보낸다. 지원하지 않는 단계 값은 건너뛴다. 앱이 단계별 지속 시간을 만들어 보내는 대신 시작과 끝을 전달한다.
4. 앱은 기록 ID·구간·선택 출처·휴대폰 시간대를 sync 전용 인증으로 전송한다. 서버는 범위·시간대·출처를 검증하고 현지 정오부터 다음 정오까지 구간을 한 날짜로 묶는다. 경과 시간은 실제 시각 차로 계산하며, 같은 단계가 겹치거나 일반 수면 구간에 상세 단계가 들어 있어도 이중으로 합산하지 않는다. 서로 다른 상세 단계가 겹치면 요청을 거절한다.
5. 수면 합계는 측정된 수면 단계와 `unspecified`의 합이다. `wake`는 별도로 세고 미기록 구간은 수면·각성에 넣지 않는다. 자동 연동의 기록 범위는 서버가 채택한 첫 단계 시작부터 마지막 단계 종료까지다. 그래프 단계 비율은 각성을 포함한 **측정된 단계 합계**를 분모로 사용한다.
6. 같은 계정의 같은 수면 날짜에 동일한 분석을 다시 보내도 추가 행이 생기지 않는다. 이 APK는 `complete_snapshot`을 보내지 않는다. 서버는 빈 배열이나 단계 없는 기록을 받아도 기존 기록을 지우지 않는다. 코칭은 계정별로 저장되며 기존 코칭 원문을 유지한다.

| 상태 | 기존 APK·서버 처리 | QA 웹 표시 |
| --- | --- | --- |
| Health Connect에서 선택한 출처 조회가 0건 | 기존 APK는 서버에 보내기 전 중단한다. 마지막 성공 시각은 그대로다. | 읽을 수 있는 기록이 없다는 안내 |
| 수면 읽기 권한 없음 | 앱이 권한 확인을 요구하고 서버로 전송하지 않는다. 연결 상태는 달잠에 저장된 동의·설정 상태일 수 있다. | 권한 경고 |
| 세션은 있지만 지원하는 단계가 0개 | 서버가 `ignored_incomplete`를 늘리고 해당 세션을 저장하지 않는다. 요청이 성공하면 마지막 동기화 시각은 갱신될 수 있다. | 제외된 기록 수 |
| 단계가 일부만 있음 | 유효한 구간을 저장한다. 내부 공백과 미기록 단계는 채우지 않는다. `ignored_incomplete`는 오르지 않는다. | 측정된 구간만 분석 |
| 동일 기록 반복 | `added_sessions=0`, `updated_sessions=0`, 기존 분석 유지 | 새로 저장한 기록 없음 |
| 서버에 빈 배열을 직접 전송 | API 호환 경로다. `200`과 추가·제외·삭제 각 0을 반환한다. 배포 APK의 0건 조회와는 전송 경로가 다르다. | 새로 저장한 기록 없음 |

테스터가 본 기존 제외 안내는 서버가 한 건 이상의 세션에서 분석 가능한 단계가 없다고 판단했다는 뜻이다. 그 메시지만으로 30일 전체 조회 결과, 정상적으로 저장된 다른 기록 수, 삼성 헬스 단계 원본 여부를 알 수 없다. 정상으로 저장한 기록이 있는지는 `added_sessions`·`updated_sessions`와 화면의 기록 목록을 함께 확인한다.

## 다음 기상 후 테스터 확인 순서

1. 갤럭시워치를 착용한 뒤 삼성 헬스에서 해당 날짜에 수면 기록과 단계 그래프가 생성됐는지 확인한다. 실제 취침·기상 시각이나 그래프 원본을 공유할 필요는 없다.
2. Health Connect의 수면 데이터에서 삼성 헬스 출처로 기록이 들어왔는지 확인한다. 삼성 헬스에서 공유가 허용됐는지, 달잠에 수면 **읽기** 권한이 있는지 각각 확인한다.
3. 달잠에서 로그인 계정과 선택 출처를 확인하고 **지금 확인**을 한 번 누른다. 연결 상태, 이전·이후 마지막 동기화 시각, 정확한 안내 문구를 적는다. 기록은 현지 정오를 경계로 묶이므로 자정을 넘긴 밤은 전날 날짜에 나타날 수 있다.
4. 대시보드가 여전히 비어 있다면 마이 → 건강앱 연결과 기록 탭을 확인한다. 확인 결과를 아래의 제한된 항목으로 공유한다.

| 전해도 되는 정보 | 확인 방법 및 한계 |
| --- | --- |
| 앱·Android 버전 | 설정의 앱 정보와 휴대전화 소프트웨어 정보에서 확인 |
| 연결·권한, 선택 출처, 마지막 동기화 시각 | 연결 표시와 Android 권한 화면을 각각 확인 |
| Health Connect 조회 세션 수·유효 단계 세션 수 | 현재 앱 화면의 진단 항목으로는 조회할 수 없다. 필요한 경우 최소 개수만 출력하는 별도 검수 빌드를 검토한다. |
| 제외 세션 수·이유 | 서버 응답의 `ignored_incomplete`는 분석 가능한 구간이 없는 세션 수다. 단계가 원래 비어 있었는지 미지원 값만 있었는지는 현 계약에서 더 나눌 수 없다. |
| HTTP 상태나 서버 코드 | 숫자 상태는 현재 APK 화면에 모두 노출되지 않는다. 담당자가 보안이 적용된 진단 기록을 조회할 수 있는 경우 400 입력 검증, 401 동기화 인증, 413 크기, 429 과다 요청, 5xx 서버를 구분한다. Health Connect 권한 거부와 0건 조회에는 HTTP 코드가 없을 수 있다. |

수면 시작과 종료 원문, 단계 타임라인, 토큰, 계정 식별자, 전송 본문은 기록하거나 전달하지 않는다. 실제 기록이 들어오기 전에는 로그를 추가하거나 다시 연결하도록 강제할 근거가 없다.

## iPhone JSON 경로

iPhone의 가져오기는 `POST /analyze` 경로로 업로드한 JSON을 검증한다. 달잠 스키마 `schema_version: 1`과 Health Export Kit `schemaVersion: 2` 변환을 테스트했다. JSON은 세션 원래 범위를 유지하고 미기록 구간을 별도로 계산한다. 자동 연동과 같은 단계 이름과 DB·그래프 필드를 사용한다.

파일 형식이나 모든 단계가 누락된 세션은 전체 가져오기가 400으로 실패한다. 다른 구간의 단계가 남아 있으면 해당 구간만 집계한다. 동일 파일, 같은 날짜의 시간대 오프셋, 잘못된 입력 이후 기존 기록 유지와 오류 안내를 합성 데이터로 검증한다. JSON 재업로드 중복 처리와 Health Connect 날짜 기준 중복 처리는 각각 독립된 경로다.

## 실행 및 후속 반영

    python -B -m unittest discover -s tests -p test_health_sync_readiness.py -v
    cd sleep_frontend
    npm run test:health-sync

건강앱 동기화 메시지와 회귀 테스트는 PR #4와 별개로 두고, PR #4 배포 이후 최신 운영 기준 위에서 검토한다. 안내 수정은 기존 Android 브리지와 API 응답으로 작동하며 APK를 재빌드할 이유가 없다. 실제 기기에서 얻은 결과를 바탕으로 조회·제외 개수의 별도 표시 필요성을 판단한다.
